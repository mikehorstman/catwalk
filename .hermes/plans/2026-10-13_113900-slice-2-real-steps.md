## Approach

Keep `StepRepository` as the single seam. Add a `StepReading` result (`steps` int?, `source` enum health|sensor|none) rather than a second counter. A `CompositeStepRepository` tries Health, then the sensor, else `none`. UI maps `none` to "Steps unavailable", never 0.

## Tasks (each ends with `flutter analyze` + `flutter test`, then commit)

1. **Verify iOS availability.** Read the `health` plugin source for `isHealthConnectAvailable` on iOS. Fix `HealthPluginClient.isAvailable` to return true on iOS. Test via the `HealthClient` fake.
2. **Distinguish null from zero.** Change `HealthClient.stepsBetween` result handling: `null` → `StepReading.none`. Failing test first in `health_step_repository_test.dart`: null → none, 0 → zero steps.
3. **Add `StepReading` + update `StepRepository`.** Update `MockStepRepository`, `HomeController`, tests.
4. **Sensor fallback.** Add `pedometer` (or the maintained equivalent — check pub.dev first). `SensorStepClient` behind the same seam. Android needs `ACTIVITY_RECOGNITION` runtime request; iOS needs `NSMotionUsageDescription` in `Info.plist`. Sensor gives steps since boot/now, so scope it to "today so far" and document that limit.
5. **`CompositeStepRepository`.** Order: Health (granted) → sensor → none. Unit-test all three branches with fakes.
6. **Home UI states.** Steps unavailable / permission denied with a re-request or "open Settings" action. Widget test: `none` shows the message, not "0".
7. **Background sync.** Add `workmanager` (Android) / background fetch (iOS) that reads the record and writes today's `DailyProgress` through `HistoryRepository`. Keep it a read-and-save; no counting. Gate behind a small test of the pure "sync today" function.
8. **Keep mocks debug-only.** Add a test/assert that `useMockSteps` is false when `dart.vm.product` is true; confirm debug buttons are hidden in release.
9. **Verify on a real device.** Simulator cannot prove this.
   - iPhone: `flutter run --release` (or `--dart-define=USE_MOCK_STEPS=false`), grant Health, walk, see steps. Deny, see fallback/unavailable.
   - Android needs a JDK (none installed) and a phone with Health Connect.

## Risks / open questions
- iOS Health returns no data vs zero data are indistinguishable when the user denied *read* access (HealthKit hides denial). The sensor fallback covers this, but "unavailable" may be unprovable on iOS. Decide: show a gentle "check Health permissions" hint.
- Pedometer-since-boot semantics differ per platform; may need a stored baseline. Could be cut if Health coverage is enough.
- iOS background execution is best-effort; do not rely on it for the 3-day runaway rule — evaluate days on app open too (already how `evaluateDay` works).
- Android builds can't be checked here until a JDK is installed.
- Decision for you: ship the sensor fallback now, or only Health + honest "unavailable" first (smaller, and the fallback comes later)?
